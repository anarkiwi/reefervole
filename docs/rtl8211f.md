# RTL8211F bring-up reference

What the board's Ethernet PHY does, as far as the sources establish it. The two Gigabit
PHYs on the Colorlight 5A-75B rev 8.x (U11 = PHY0, U13 = PHY1) are Realtek
`RTL8211FP`, register-compatible with the `RTL8211F(I)/RTL8211FD(I)` datasheet — measured
so, though they report a different part ID than that datasheet gives (§8.9).

Section 8 holds the bench measurements; where one contradicts a source, the measurement is
marked in place and §8 carries the evidence.

Sources, in order of authority:

| Tag | Source |
| --- | --- |
| **DS** | *RTL8211F(I)/RTL8211FD(I) Datasheet*, Rev. 1.1, 21 Feb 2014 (marked DRAFT). Cited by section and printed page. Not redistributable; kept in the gitignored `vendor/datasheets/` |
| **CH** | [chubby75](https://github.com/q3k/chubby75/tree/master/5a-75b) `hardware_V8.2.md` / `hardware_V8.0.md`, "Gigabit PHYs (U11 & U13)" |
| **LK** | Linux `drivers/net/phy/realtek.c` (v6.12). Known-working code; the only source for the RGMII delay registers |
| **LE** | LiteEth `liteeth/phy/ecp5rgmii.py`, the FPGA side we have to match |

Read together with [`board.md`](board.md), which summarises the hazards this reference
documents in full.

## 1. Straps

Six configuration inputs are multiplexed onto the PHY's own RGMII **receive** pins, so
the FPGA cannot set them: they are board resistors. Pin type `O/LI/PU` or `O/LI/PD` =
output, latched input during power-up or reset, with an internal pull-up or pull-down
(DS §6, p.7; §6.6 Table 6, p.9; §7.8 Tables 10–11, p.15).

| PHY pin | Strap | Internal pull | Unstrapped value | Pulled high (4.7 kΩ to DVDD_RG) | Pulled low (4.7 kΩ to GND) |
| --- | --- | --- | --- | --- | --- |
| 22 RXD3 | `PHYAD[0]` | PU | 1 | address bit 0 = 1 | address bit 0 = 0 |
| 27 RXC | `PHYAD[1]` | PD | 0 | address bit 1 = 1 | address bit 1 = 0 |
| 26 RXCTL | `PHYAD[2]` | PD | 0 | address bit 2 = 1 | address bit 2 = 0 |
| 23 RXD2 | `PLLOFF` | PD | 0 | PLL stops on entering ALDPS | PLL keeps toggling in ALDPS |
| 24 RXD1 | `TXDLY` | PD | 0 | +2 ns internal delay on TXC | no internal TX delay |
| 25 RXD0 | `RXDLY` | PU | 1 | +2 ns internal delay on RXC | no internal RX delay |

`LED0/1/2` additionally strap `CFG_EXT` and `CFG_LDO[1:0]` (RGMII I/O voltage); not
brought out to the FPGA and not relevant here.

**Address arithmetic.** The MDIO `PHYAD` field is 5 bits; the upper two are always 0, so

```
address = 4·PHYAD[2] + 2·PHYAD[1] + PHYAD[0]      (RXCTL, RXC, RXD3)
```

Legal range is 1–7 (DS Table 11, p.15). Address 0 is a broadcast that every PHY answers;
it can be suppressed with `PHYCR1` bit 13 = 0. A PHY strapped to 0 can be made to latch
the first non-zero address it sees, if `PHYCR1` bit 6 = 1.

With no strap resistors stuffed the internal pulls give **address 1** on both PHYs, which
would collide on the shared MDIO bus, so at least one address strap must be stuffed on
this board. **Measured: the two PHYs are at addresses 1 and 2** (§8.2). So one PHY is
entirely unstrapped and the other has two resistors — RXD3 pulled low, and `PHYAD[1]`
pulled high. Address 0 does not answer, because bit 13 of `PHYCR1` reads 0 and not the 1
the DS default column gives.

**Conflict, unresolved:** CH labels RXCTL as `PhyAddr1` and RXC as `PhyAddr2`; DS Tables 6
and 10 both say RXC = `PHYAD[1]`, RXCTL = `PHYAD[2]`. DS wins on authority, but this board
cannot arbitrate: address 2 is `PHYAD[1]` alone, which either mapping yields, differing only
in which pin carries the resistor (§8.2). Nothing here depends on the answer — addresses are
discovered by scanning, never computed.

**Latch timing.** Straps are sampled while `PHYRSTB` is low and latched as it releases
(DS §6, p.7 — "latched input during power up or reset"). A hardware reset therefore
re-samples them and returns every register to its default (DS §6.5, p.9; §7.17, p.28).
`PHYRSTB` must be held low ≥ 10 ms, and register access must wait a further 30 ms after
release. On this board `PHYRSTB` is shared and PHY1 sources the FPGA's clock, so none of
that is reachable from gateware — see §6.

The ECP5 drives nothing on these nets, but its configuration-time pull-ups would fight a
4.7 kΩ strap; the constraint file must set `PULLMODE=NONE` on RXD[3:0], RXC and RXCTL.

## 2. RGMII internal delay

`TXDLY`/`RXDLY` each insert a fixed **2 ns** delay (DS §6.6 Table 6, p.9):

| Strap | Effect when 1 |
| --- | --- |
| `TXDLY` | PHY delays the incoming TXC by 2 ns before latching TXD — the MAC may send TXC edge-aligned |
| `RXDLY` | PHY delays the outgoing RXC by 2 ns — RXC arrives centred in the RXD eye at the MAC |

DS §7.8 Table 11 (p.15) describes `TXDLY` with the same wording as `RXDLY` ("delay to RXC
for RXD latching"). That is a copy-paste error in the datasheet; Table 6 on p.9 has the
correct TXC/TXD wording, and LK's naming agrees.

**Software override.** The datasheet documents no register for either delay — its extension
page list (DS §8.3 Table 21, p.30) contains only page `0xd04`, and page `0xd08` appears
nowhere in the document. LK is the only source, and it is explicit that these registers
hold the strapped value and can be rewritten:

| Page | Reg | Bit | Meaning |
| --- | --- | --- | --- |
| `0xd08` | `0x11` | 8 | 2 ns TX delay (`TXDLY`) |
| `0xd08` | `0x15` | 3 | 2 ns RX delay (`RXDLY`) |

LK's `rtl8211f_config_init()` writes exactly these to implement `rgmii`, `rgmii-txid`,
`rgmii-rxid` and `rgmii-id`, and logs whether the write changed "the value from
pin-strapping RXD1/RXD0 or the bootloader". So: **the straps are readable and overridable
over MDIO**, and reading those two bits at P1 answers the question outright rather than
requiring a board inspection.

**Consequence for the FPGA side.** LE applies its `tx_delay` to the TXC output and its
`rx_delay` to the RXD/RXCTL *inputs*, both through ECP5 `DELAYG` at 25 ps per tap, capped
at 127 taps (3.175 ns). The two delays are therefore complementary, not additive:

| PHY strap | LE parameter | Start value | Taps |
| --- | --- | --- | --- |
| `TXDLY` = 0 | `tx_delay` | 2.0 ns | 80 |
| **`TXDLY` = 1 — this board** | `tx_delay` | ~0 ns | **0** |
| **`RXDLY` = 1 — this board** | `rx_delay` | ~0 ns (trim upward) | **0–16** |
| `RXDLY` = 0 | `rx_delay` | 2.0 ns | 80 |

Both straps read 1 on both PHYs (§8.1), so both LiteEth instances are built with
`tx_delay = rx_delay = 0`. LE's own defaults are `tx_delay = rx_delay = 2e-9`, which is only
correct for a PHY with both delays strapped off — the opposite of this board, where they
would stack a second 2 ns on a clock the PHY has already delayed. The target window is DS
Table 58 (p.63): `TskewR` (data-to-clock skew at a receiver) 1.0–2.6 ns, typical 1.8 ns.

## 3. RGMII in-band status

The datasheet **never mentions in-band status**. "In-band", "inter-frame" and any
description of RXD[3:0] behaviour outside a frame are absent from all 73 pages; DS §7.11.1
(p.18) covers only clock rates and data transitions. There is no register documented to
enable or disable it, and no page in DS §8.3 that could hold one.

LE's `LiteEthPHYRGMII(with_inband_status=True)` (the default) samples `rx_data[3:0]` while
`rx_ctl == 0b00` and decodes bit 0 = link up, bits 2:1 = speed (`00` 10M, `01` 100M,
`10` 1G), bit 3 = full duplex. That is the RGMII v2.0 encoding, which the RTL8211F very
likely implements — but nothing in the sources establishes it, and nothing establishes
whether it is on by default or how to turn it off.

It does implement it, and with nothing written: measured `0x0d` on both ports of a rev 8.2
board linked at 1000BASE-T full, agreeing with MDIO and with the link partners. See §8.4 for
the readings. The fallback, if a future part disagrees, is `with_inband_status=False` plus
MDIO polling, which costs nothing but latency on link-state change.

target register, write 31 back to 0.

Two source discrepancies worth knowing before writing an MDIO driver:

* **INSR address.** DS §8.4.19 titles it "Address 0x13" and DS §7.5 calls it "Register 19",
  but its own bit rows are numbered `29.x` and DS Table 19 lists offset 29. LK uses
  `0x1d` = 29. Use 29.
* **Page for registers 24/25/29.** DS presents them as page 0. LK reads and writes all
  three via `phy_read_paged(phydev, 0xa43, ...)`. Page `0xa43` is not mentioned in DS at
  all. Read them both ways at P1 and use whichever returns sane values.

## 5. CLKOUT and the 25 MHz system clock

CLKOUT is pin 35, "125/25 MHz reference clock generated from internal PLL" (DS §6.2 Table 2,
p.7). On rev 8.x it is PHY1's CLKOUT that feeds PHY0's `XTAL_OUT/EXT_CLK` and FPGA pin `P6`
(CH). It is a **separate pin from RXC** and is not part of the RGMII group.

`PHYCR2` (register 25) is therefore as dangerous as BMCR on PHY1: bit 0 gates CLKOUT and
bit 11 selects its frequency. Firmware must treat register 25 on PHY1 as read-only.

DS gives bit 25.11 a **default of 1 = 125 MHz**, which contradicts CH's measured 25 MHz on
`P6`. **CH is right:** `P6` measures 24.94 MHz while bit 11 reads 1 on both PHYs (§8.3), so
the DS default column — or the bit's sense — is wrong for this part. The PLL is constrained
against the measurement, 25 MHz, and the gateware never writes register 25.

ALDPS is a second way to lose the clock. With `PHYCR1` bit 2 (ALDPS enable) set *and* the
`PLLOFF` strap high, the PLL stops when the cable is unplugged. DS defaults ALDPS to
disabled and the `PLLOFF` pin pulls down internally, and both PHYs were measured that way —
`PHYCR1` = `0x0118`, bits 12, 2 and 1 all clear (§8.8), so the as-found state is safe. But
LK's `realtek,aldps-enable` path sets bits 12, 2 and 1 of `PHYCR1` together, which on this
board would stop the FPGA's clock the moment PHY1's cable is pulled. **Never set `PHYCR1`
bits 12, 2 or 1 on PHY1.**

## 6. Reset, power-down, isolate

| BMCR bit | Datasheet says | Effect on CLKOUT | Safe here? |
| --- | --- | --- | --- |
| 15 reset | BMCR and BMSR return to defaults; may change the internal PHY state and the link state (DS Table 22, p.30) | **Not stated.** LK issues `genphy_soft_reset()` immediately *after* changing the CLKOUT enable bit, implying a soft reset is what makes a CLKOUT change take effect — so it does act on the clock path | **No.** Forbidden on both PHYs |
| 11 power-down | Only the management interface and logic stay active; link goes down (DS Table 22, p.31) | **Not stated.** Powering down the analog blocks that contain the PLL is the obvious reading | **No.** Forbidden on both PHYs |
| 10 isolate | RGMII is isolated; MDC/MDIO stay active; TXD[3:0] and TXCTL are ignored; TXC, RXC, RXCTL and RXD[3:0] are driven high-impedance (DS Table 22, p.31) | **None.** Measured on both PHYs, including the one that sources the clock: `P6` stayed at 25.0 MHz throughout (§8.7) | **Yes.** Measured, and undone by the same MDIO write |

Isolate is the safe way to quiesce a port ([`board.md`](board.md)), and that is now a
measurement rather than an inference from the datasheet's enumerated pin list (§8.7). Three
things it does *not* do matter more than the clock question it settles:

* **The line side stays up.** `BMSR` link, `LPA`, `ANER` bit 0 and the link partner's own
  carrier are all unchanged by isolate. It quiesces the RGMII side only, so neither MDIO nor
  the far end can tell you a port is isolated — only the register you wrote can.
* **`inband_status` freezes rather than falling.** RXC goes high-impedance, the `ethN_rx`
  domain stops, and LE's `inband_status` CSR keeps returning whatever it last decoded: an
  isolated port reads `0x0d` — "link up, 1000, full" — indefinitely. A design that polls
  in-band status to notice a dead port will not notice this one.
* **RXC stops, so the `eth0_rx`/`eth1_rx` clock domain stops.** Every CDC across it must
  tolerate a stopped clock, and the isolated port's RX-side logic must be held in reset
  rather than assumed to be ticking. Measured on a datapath that did not: with traffic
  flowing, isolating one port latched a fault on the *opposite* direction, closed that
  direction's commit permanently, and needed an SRAM reload to clear. The board survives
  isolate unconditionally; a datapath survives it only if it was written for this.

Two further consequences of the shared `PHYRstB` and PHY-sourced clock:

* `LiteEthPHYRGMII(with_hw_init_reset=True)` — the LE default — drives `pads.rst_n`. The
  platform definition must not expose an `rst_n` pad for either PHY, and both instances
  must be built with `with_hw_init_reset=False`.
* Auto-negotiation restarts by itself after any hardware or software reset regardless of
  BMCR bit 9 (DS Table 22, Note 3), and a power-down→normal transition performs an implicit
  soft reset and AN restart (DS Table 22, Note 1). There is no "quietly re-init the PHY"
  path that avoids the clock risk.

## 7. MDIO bus

Standard IEEE 802.3 clause 22 framing, 32-bit preamble, one shared bus for both PHYs
(DS §7.11.2 Tables 12–13, p.18). Timing limits (DS Table 57, p.60): MDC period ≥ 80 ns
(≤ 12.5 MHz), high and low pulses ≥ 32 ns, MDIO setup and hold 10 ns, MDIO valid from MDC
rising edge ≤ 300 ns. Preamble suppression is always accepted (BMSR bit 6), and preamble
checking can be turned off with `PHYCR1` bit 4. The bus needs a 1.5 kΩ pull-up, which the
board provides.

At 62.5 MHz `sys`, a divide-by-8 MDC (7.8 MHz) is inside spec; divide-by-16 (3.9 MHz)
gives margin for the 300 ns read-valid time and costs nothing at our access rate.

**The read turnaround is one sampled bit, not two.** A read frame is 64 bit times like a
write, but the master releases MDIO during the first turnaround bit, so the first level it
can sample is already the PHY's zero; the sixteen data bits follow immediately and the last
bit time is the released trailer. Sampling two turnaround bits shifts every value one place
left, which is invisible on registers whose top bit is 0 — BMCR, BMSR, PHYID1 all still look
plausible — and only shows up on one whose top bit is set. On this board that is PHYID2:
`0xc858` read as `0xffff`, i.e. as "no PHY here", and the first bench scan reported an empty
bus with both PHYs answering perfectly. Linux `mdiobb.c` does it correctly: one
`mdiobb_get_bit` for the turnaround, sixteen for the data, one to release. So does
`tools/phy_probe.py`, and `tests/test_phy_probe.py` pins it with an emulated slave pair.
**The P1 gateware MDIO master must do the same.**

## 8. Measurements and what is still open

Measured on the bench board — Colorlight 5A-75B rev 8.2, serial console unwired — with
`tools/phy_probe.py` over jtagbone against `reefervole/gateware/diagnostics.py`. §8.1–§8.3
and §8.6–§8.9 were taken with neither RJ45 cabled; §8.4, §8.10 and §8.11 need both cabled to
gigabit NICs. The board has never been reset, and the only PHY registers ever written are 31
(page select, always restored) and, in §8.7 alone, BMCR bit 10, which was cleared again.
Raw output is reproduced under each answer; rerun with:

```sh
python3 tools/jtagbone_server.py &
python3 tools/phy_probe.py --csr-csv build/phase1a/csr.csv
```

### 8.1 Which delay straps are stuffed, per PHY? — **both, on both PHYs**

```
addr  1  0x11=0x0d09 bit8=1  0x15=0x0819 bit3=1
addr  2  0x11=0x0d09 bit8=1  0x15=0x0819 bit3=1
```

`TXDLY` = 1 and `RXDLY` = 1, identically on both PHYs. Nothing had written those registers,
so they hold the strapped value (LK's wording in §2). `RXDLY` = 1 is the unstrapped state of
RXD0's internal pull-up, but `TXDLY` = 1 is not: RXD1 pulls down internally, so the board
stuffs a pull-up there deliberately.

**The PHY already inserts both 2 ns delays, so the FPGA must add neither.** By the table in
§2 that is `tx_delay = rx_delay = 0`, i.e. zero `DELAYG` taps on both directions of both
ports. LE's `2e-9`/`2e-9` defaults are wrong here in the worst direction — they would add a
second 2 ns to a clock the PHY has already delayed, which is a full bit time at 125 MHz.
The phase-1b sweep is therefore a trim around 0, not a search: raise `rx_delay` in single
taps only if the RX eye needs it, and leave `tx_delay` at 0.

### 8.2 What are the two PHY addresses? — **1 and 2**

```
== MDIO scan, addresses 0-31 ==
  addr  1            id 0x001c.c858  OUI 00:e0:4c model 0x05 rev 8
  addr  2            id 0x001c.c858  OUI 00:e0:4c model 0x05 rev 8
```

Exactly two responders across all 32 addresses. Firmware scans and uses what it finds; these
are the two addresses to expect.

Two consequences the scan settles on the way past:

* **Address 0 does not answer**, so the broadcast is off. `PHYCR1` reads `0x0118`, whose bit
  13 is 0 — the DS default column (bit 13 = 1) is wrong for this part, as it is for bit 11 of
  `PHYCR2` in §8.3. Bit 6 is also 0, so neither PHY is a latch-first-address part strapped
  to 0; both addresses are real straps.
* **Which PHY is at which address is not yet known.** Both were read with no cable attached,
  so their registers are identical to the bit. Cabling one port and reading `PHYSR` bit 2
  identifies them; that is P1 work, and it matters because PHY1 is the one whose registers 24
  and 25 must be treated as read-only.

**The CH-versus-DS strap conflict is *not* settled, and this board cannot settle it.** Only
addresses 3 and 5 separate the two readings. Address 2 is `PHYAD[1]` alone, which either
mapping produces — DS if the stuffed pull-up is on RXC, CH if it is on RXCTL — and MDIO
cannot see which pin carries the resistor. Address 1 is the fully unstrapped state and says
nothing either. Deciding it needs a board inspection, and nothing in this design depends on
it: the addresses are discovered by scanning, never computed from the strap mapping.

### 8.3 Is CLKOUT 25 MHz, and is `PHYCR2` bit 11 really 1? — **25 MHz, and yes, and they contradict**

```
== clk25, FPGA pin P6 from PHY1 CLKOUT ==
  alive=yes done=yes count=843577 -> 24.9394 MHz
  addr  1  PHYCR2=0x0841 bit11=1
  addr  2  PHYCR2=0x0841 bit11=1
```

CH is right and the DS default column is wrong. `P6` carries 25 MHz while `PHYCR2` bit 11
reads 1, which DS Table 38 says selects 125 MHz. Bit 0 reads 1, so CLKOUT is enabled, as it
must be for the FPGA to be running at all.

The counter is a ratio against the ECP5 `OSCG`, which the bitstream assumes is 31.000 MHz,
so `OSCG` accuracy — not the counter — bounds the absolute figure. Read the other way: if
`P6` is exactly 25 MHz then `OSCG` is 31.065 MHz, 0.21% high, which is ordinary for that
oscillator; for `P6` to be 125 MHz, `OSCG` would have to be 155 MHz. Three runs gave 843577,
843780 and 843896 counts, a spread of 0.04%. **The PLL is constrained against 25 MHz.**

### 8.4 Does the RTL8211F emit RGMII in-band status, and is it on by default? — **yes, and yes**

Measured with both RJ45s cabled to gigabit NICs and a design that instantiates both
`LiteEthPHYRGMII`s. LE's `inband_status` CSR read `0x0d` on both ports:

```
ethphy0_rx_inband_status = 0x0d   link=up  clock_speed=0b10 (1000M)  duplex=full
ethphy1_rx_inband_status = 0x0d   link=up  clock_speed=0b10 (1000M)  duplex=full
```

Three independent witnesses agreed at the same moment: MDIO on the same board
(`BMSR = 0x79a9`, autoneg-complete set; `LPA = 0xc5e1`; `GBSR = 0x78ff` and `0x38ff`, a
1000-full-capable partner), the host NICs' own `ethtool` (`1000Mb/s`, `Full`), and 920 302
frames crossing the board at 909 Mbit/s with none dropped. The RGMII v2.0 encoding in §3 is
what the part emits, it is on with no register written, and `with_inband_status=True` — and
therefore `with_dynamic_link=True` — can be relied on.

Still unmeasured at 10 and 100 Mb/s: the board advertises gigabit only (§8.10), so a
lower-speed link needs `ANAR` written first.

### 8.5 Is there a register that disables in-band status? — open, and now moot

Still not answerable from these sources, and §8.4 came back right, so nothing needs it.

### 8.6 Are registers 24/25/26/29 on page 0 or page `0xa43`? — **both; they are the same registers**

```
  phy 1 page 0x000: 24=0118 25=0841 26=1002 29=0000
  phy 1 page 0xa43: 24=0118 25=0841 26=1002 29=0000
```

Read on page 0 and again through a `0xa43` page select, both PHYs returned identical values.
DS presents them as page 0 and LK reaches them through `0xa43`; both work because page
`0xa43` aliases page 0 for these registers. **Use page 0** — it is one MDIO frame instead of
three, and it is what the DS documents.

Register 29 corroborates the alias: it read `0x0020` on its first access and `0x0000` on
every later one, which is the read-to-clear behaviour DS Table 40 gives INSR at offset 29.

### 8.7 Does BMCR isolate leave CLKOUT running? — **yes, on both PHYs, measured**

Isolate does not touch CLKOUT. `P6` kept ticking with bit 10 set on PHY0, and again with it
set on PHY1 — the PHY that generates the clock — held for over thirty seconds. Counts are
`clk25` edges per 2^20 `sys` cycles, so a stopped clock reads as a count near zero rather
than as a small error:

```
baseline                       count=253911 -> 25.0220 MHz
isolate phy 1 (PHY0)  +0.5 s   count=253765 -> 25.0076 MHz
                      +3.5 s   count=253853 -> 25.0163 MHz
release phy 1         +3.5 s   count=253944 -> 25.0253 MHz
isolate phy 2 (PHY1)  +0.5 s   count=253958 -> 25.0266 MHz
                      +3.5 s   count=254048 -> 25.0355 MHz
                     +30   s   count=254218 -> 25.0523 MHz
release phy 2         +3.5 s   count=253942 -> 25.0251 MHz
```

The spread is 0.18%, the same order as the `OSCG` timebase's own drift, and `alive` never
dropped. Both PHYs kept `BMSR` link, `LPA = 0xc5e1` and `ANER` bit 0 set throughout, and
neither bench NIC's `carrier_changes` moved: the line side is untouched.

**How to run it without risking a power cycle**, which is why this could be done on the
bench board rather than on a spare. Load a bitstream whose `sys` comes from `OSCG` and not
from `clk25` — `reefervole/gateware/diagnostics.py` is exactly that — so jtagbone and the
MDIO master keep working even if CLKOUT does stop. The `clk25` meter then *reports* the
answer instead of the board going silent, and the same MDIO write undoes it. Identify the
clock-sourcing PHY first (§8.11) and do the other one first anyway. Repeating it afterwards
against a `clk25`-clocked forwarding design confirmed the practical case: the CSR bus stayed
up, `ctrl_scratch` round-tripped and `ctrl_bus_errors` stayed 0 with either PHY isolated.

`tools/phy_probe.py`'s write guard is per bit rather than per register because of this
result: BMCR bit 10 is writable, bits 15, 11 and the still-unmeasured 9 are not, and the
guard refuses a write that would *change* a protected bit rather than one that fails to zero
it — PHYCR2's CLKOUT enable is safe only as the 1 the board came up with.

### 8.8 Does the PHY come up with ALDPS disabled? — **yes, on both**

`PHYCR1` reads `0x0118` on both PHYs: bits 12, 2 and 1 are all 0, so ALDPS, its PLL-off and
its XTAL-off are all disabled out of reset. The `PLLOFF` strap is therefore moot in the
as-found state, and the firmware check in §5 is a guard against a future write rather than
against the power-on state.

### 8.9 The part is not the one the datasheet describes

Both PHYs report PHYID1:PHYID2 = `0x001c.c858`: Realtek's OUI `00:e0:4c`, but model `0x05`
revision `8`, where DS Tables 24–25 give model `0b010001` revision `0b0110`, i.e.
`0x001c.c916`. Linux's `realtek` driver has no exact or model match for `0x001cc858`; it
would bind through the `PHY_ID_MATCH_VENDOR(0x001cc800)` catch-all.

Register *behaviour* matches the DS map everywhere it was checked — BMCR `0x1040`, BMSR
`0x7989`, 1000BASE-T control `0x0200`, extended status `0x2000`, the page-31 select, the
`0xd08` delay registers, `PHYCR1`/`PHYCR2` — so the map in §4 stands. What does not stand is
DS's **default** column: bit 11 of `PHYCR2` and bit 13 of `PHYCR1` both differ from it. Treat
DS defaults as unverified and read the register.

### 8.10 The PHYs advertise 1000BASE-T full duplex and nothing else

`ANAR` (register 4) reads `0x0001` on both PHYs — the IEEE 802.3 selector field with **no**
technology bits, so no 10 or 100 Mb/s ability is offered — while `GBCR` (register 9) reads
`0x0200`, 1000BASE-T full. DS gives `ANAR` a reset default of `0x01e1`; this part does not.

The consequence is a bench trap rather than a design one. **A link partner that advertises
only 10/100 will never link to this board**, and it will not link *slowly*: autonegotiation
finds no common technology and the port stays down, with `LPA = 0` and `ANER` bit 0 clear as
though nothing were plugged in at all. Two-pair patch cables produce the same symptom from
the other direction, since gigabit needs all four. Cable the rig with gigabit NICs and
four-pair cable, and it comes up at 1000BASE-T full on both ports with no register written:

```
phy 1: BMCR=1040 BMSR=79a9 ANAR=0001 LPA=c5e1 ANER=006f GBCR=0200 GBSR=78ff
phy 2: BMCR=1040 BMSR=79a9 ANAR=0001 LPA=c5e1 ANER=006f GBCR=0200 GBSR=38ff
```

Note `BMSR` bit 2: it is latching-low, so the first read after a link comes up reports the
old state. Read it twice, or read `LPA` and `ANER` bit 0, which do not latch — those are also
what distinguish "no partner has ever been seen" from "a partner is there and we disagree".

Writing `ANAR` to offer 10/100 is permitted by the write guard in §7 — it protects named
bits of registers 0, 24 and 25, not whole registers — but it does not take effect until
autonegotiation restarts, and that is `BMCR` bit 9, which the guard does refuse: unlike bit
10 it has not been measured against CLKOUT, and §6 explains what is at stake.

### 8.11 Which MDIO address is which PHY? — **addr 2 is PHY1, the clock source**

Nothing in the register map says which responder is `eth:0` and which is `eth:1`, and it
matters: PHY1 sources CLKOUT, so it is the one to poke last. One bench NIC taken
administratively down settles it in seconds, with no write to any PHY:

```
both NICs up          phy 1 link=1 LPA=c5e1   phy 2 link=1 LPA=c5e1   inband0=0x0d inband1=0x0d
NIC on bsw-a down     phy 1 link=1 LPA=c5e1   phy 2 link=0 LPA=0000   inband0=0x0d inband1=0x00
```

The PHY that lost `LPA` and the `ethphyN` whose `inband_status` fell are the same device, so
**MDIO address 2 is `ethphy1`, i.e. PHY1 and the CLKOUT source; address 1 is `ethphy0`**.
The two are also distinguishable by their 1000BASE-T roles on this board — `GBSR` bit 14
reads 1 at address 1 and 0 at address 2, master and slave — but that is a negotiated result
that can swap, so map it with the cable, not with the register. Straps differ per board:
re-derive the mapping rather than copying these addresses.

# Bench setup

How to wire a Colorlight 5A-75B for development: power, JTAG, console, and a two-NIC test
rig. Pin data is from [chubby75](https://github.com/q3k/chubby75/tree/master/5a-75b); the
board itself is described in [`board.md`](board.md).

**Read §3 before applying power.** It is the only step that destroys hardware.

## 1. What you need

| Item | Why | Notes |
| --- | --- | --- |
| Colorlight 5A-75B, **rev 8.2** | The target | Also fine: 8.0, 7.0. Avoid 6.1 — its second Ethernet port is mis-pinned upstream ([`board.md`](board.md) §5) |
| 5 V PSU, ≥ 2 A, **5.5 V absolute maximum** | Board power | See §3 |
| FT232H breakout | Loading bitstreams | MPSSE JTAG, 3.3 V, driven natively by openFPGALoader; §4. An FT2232H, Tigard or Digilent HS2 works the same way |
| 3.3 V USB-UART adapter | Console | CP2102, FT232R or CH340 **switched to 3.3 V** |
| ~470 Ω resistor | Protects the UART adapter | See §5 — the button shares the UART RX net |
| 2 spare Ethernet NICs | Traffic either side of the board | Onboard + USB3 GbE is fine; they must be free of production traffic |
| 2 Ethernet patch cables | Host ↔ board | Cat5e or better |
| Fine jumper wires, soldering iron | The JTAG and UART pads are unpopulated | 0.1 in header soldered into J27–J34 is the durable option |

Optional but useful: a second board, so a bricked one does not stop the work; and a
passive Ethernet tap or a managed switch with port mirroring, for verifying §6.

## 2. Bitstreams without a local toolchain

Everything builds in the project image, so nothing has to be installed on the bench host
but openFPGALoader and a terminal emulator:

```sh
docker run --rm -v "$PWD:/work" reefervole make -C /work check
```

See [`toolchain.md`](toolchain.md).

## 3. Power — the one irreversible mistake

The 5 V rail feeds the FPGA buck converters and the level shifters directly. **The maximum
input is 5.5 V.** These boards are sold for LED panels, which commonly run from 12 V
supplies, and a 12 V supply on the 5 V input destroys the board immediately.

* Verify the supply with a meter *before* connecting it.
* Connect ground first, then 5 V.
* Power the board from its own supply, not from the JTAG or UART adapter.
* Leave the board unpowered while you solder and wire everything below.

## 3a. Rev 8.x — do not reset the PHYs

The FPGA's 25 MHz clock is generated by PHY1 and `PHYRstB` is shared by both PHYs, so
resetting either PHY stops the system clock and the board is dead until it is
power-cycled. When poking at the PHYs by hand: **no BMCR bit 15 (reset), no bit 11
(power-down)**, and treat `PHYCR2` on PHY1 as read-only. A power cycle always recovers
it — this is a lockout, not damage. Full rules in [`board.md`](board.md) §3.

## 3b. The whole rig at a glance

## 4. JTAG with an FT232H

openFPGALoader drives an FT232H in MPSSE mode over libusb. **The cable name is `ft232`,
which is a trap**: that entry is VID `0x0403` PID `0x6014`, which is the FT232**H**. The
FT232R is PID `0x6001` and is a different, bit-banged cable. Confirm with `lsusb`:

```
$ lsusb | grep 0403
  0403:6014  ->  -c ft232     FT232H, what you want
  0403:6001  ->  not this     FT232R, bit-bang only
```

### Check the adapter before you solder

The board's JTAG pads are unpopulated, so wiring them is a commitment. Prove the host side
works first, with nothing attached to the FT232H but USB:

```sh
openFPGALoader --scan-usb          # must list 0403:6014
```

That exercises exactly the path that fails for permissions or driver reasons — libusb
open, kernel detach, MPSSE init — and it needs no target. If it lists the cable, every
later failure is wiring or the board, which is a much smaller search.

### The FT232H cannot also be your console

Its USB descriptor says "USB-UART/FIFO", which invites the assumption that one FT232H can
serve both jobs. It cannot: MPSSE and UART are mutually exclusive modes of the same single
channel, and openFPGALoader owns the device while it is bitstreaming. The console in §5
needs its own 3.3 V USB-UART adapter.

### Wiring

MPSSE fixes the four JTAG signals to the low nibble of the ADBUS port. openFPGALoader
configures the direction mask as `0x0B` — ADBUS0, 1 and 3 driven, ADBUS2 sampled — so the
mapping is not adjustable and there is nothing to configure:

```
   FT232H breakout                     5A-75B pads, next to the FPGA (U33)
   +---------------------+             +-----------------------------------+
   | ADBUS0   D0   TCK   |------------>| J27   TCK                         |
   | ADBUS1   D1   TDI   |------------>| J32   TDI                         |
   | ADBUS2   D2   TDO   |<------------| J30   TDO                         |
   | ADBUS3   D3   TMS   |------------>| J31   TMS                         |
   |          GND        |-----+-------| J34   GND     <- connect first    |
   |                     |     |       | J33   3.3 V   <- leave open       |
   | 3V / 5V   leave open|     |       +-----------------------------------+
   +---------------------+    ===
                                        board pad assignments are identical
   ADBUS4..7 and ACBUS unused           on rev 6.1, 7.0, 8.0 and 8.2
   -- leave them unconnected: the OpenOCD config litex_server uses drives
      ADBUS5..7 high, harmlessly only because nothing is wired to them
```

Silkscreens vary. Adafruit's breakout labels these `D0 D1 D2 D3`; FTDI's UM232H and most
generic boards label them `AD0..AD3` or `ADBUS0..3`. Some boards also print the SPI names
`SK DO DI CS`, which map to TCK, TDI, TDO, TMS in that order.

### Three things to get right

* **Do not connect the board's `J33`.** The FT232H has no VTref sense — unlike a J-Link,
  which needs it — and the board has its own regulated supply. `J33` stays open, and so do
  the breakout's `3V` and `5V` pins. Ground is the only rail shared.
* **FT232H I/O is 3.3 V**, which is what the ECP5 banks want, so no level shifting and no
  series resistors on the JTAG lines. (The UART in §5 is the one that needs a resistor, for
  an unrelated reason.)
* **The kernel may claim the device first.** `ftdi_sio` binds FTDI parts and presents them
  as `/dev/ttyUSB*`; openFPGALoader detaches it automatically, but if you see a claim error,
  `sudo rmmod ftdi_sio` or a udev rule fixes it. The rules file in §7 covers this.

Keep the wires under about 10 cm. If `--detect` is flaky, drop the clock with
`--freq 1000000` before suspecting the board.

### If you would rather use OpenOCD

```sh
openocd -c "adapter driver ftdi; ftdi vid_pid 0x0403 0x6014; ftdi channel 0" \
        -c "ftdi layout_init 0x0008 0x000b; transport select jtag; adapter speed 1000" \
        -c "jtag newtap ecp5 tap -irlen 8 -expected-id 0x41111043"
```

`layout_init 0x0008 0x000b` is the same initial value and direction mask openFPGALoader
uses, so the two agree on the pin mapping above.

## 5. UART — the console

The board has no dedicated UART. The console runs on the two J19 signals, which are shared
with the status LED and the button:

| Board signal | rev 8.0 / 8.2 | rev 7.0 | rev 6.1 | Direction | Adapter |
| --- | --- | --- | --- | --- | --- |
| `DATA_LED-` | T6 | P11 | U16 | board → host | RXD |
| `KEY+` | R7 | M13 | R16 | host → board | TXD, **through ~470 Ω** |
| GND | — | — | — | — | GND |

```
   USB-UART (3.3 V)                board J19 / rev 8.2 pins
   +----------+                    +-----------------------------+
   |      RXD |<-------------------| T6   DATA_LED-   board -> host
   |          |                    |                             |
   |      TXD |-----[ 470R ]------>| R7   KEY+        host -> board
   |          |            ^       |                             |
   |      GND |------------|-------| GND                         |
   |      VCC |  no connect|       +-----------------------------+
   +----------+            |              |
                           |             ---  button J28 shorts KEY+ to GND
                     the resistor is       |   when pressed; without the
                     what saves the        |   resistor that shorts TXD
                     adapter's driver     ===
```

Do not connect the adapter's VCC.

Three consequences of sharing those pins, all design constraints rather than bugs:

* **Put ~470 Ω in series with the adapter's TXD.** `KEY+` is the button net, pulled up with
  10 kΩ and shorted to ground when the button is pressed. Without the resistor, pressing
  the button while the adapter drives the line high shorts its output driver.
* **Pressing the button injects a break onto UART RX.** Treat the button as unusable.
* **The status LED flickers with console traffic** and cannot be used as an indicator. On
  rev 6.1 the capacitance on `KEY+` also limits the link to 9600 baud; rev 7.0 and later
  run at 115200. Design console output to be readable at 9600: no banners, no box drawing,
  fixed-width one-line records.

Use the stable path, not `/dev/ttyUSB0`, which moves on replug:

```
picocom -b 115200 /dev/serial/by-id/usb-Silicon_Labs_CP2102_...-if00-port0
```

## 5b. Before the Ethernet adapters arrive

JTAG and the console alone settle everything about the board that a design has to be built
around, with no cables in the RJ45s. The bring-up design in
`reefervole/gateware/diagnostics.py` requests no `eth` pads for exactly this reason. It is a
`SoCMini` with four things in it: a PLL clocked from the ECP5's internal `OSCG` rather than
`clk25`, so it runs even if the PHY clock is absent; `jtagbone`, so the host reaches its CSRs
over the same FT232H that loaded it; a `LiteEthPHYMDIO` master; and a gate-counter that times
`clk25` against `OSCG`. A gateware-only UART echo on J19 comes back character for character
if and only if TX, RX, ground, the series resistor and the baud rate are all right — no CPU
and no firmware needed to prove the console.

`tools/phy_probe.py` drives it from the host through `litex_server --jtag`; its `--help`
prints the exact `litex_server` invocation and the OpenOCD config the bridge needs, and the
list of registers it refuses to write. `--dry-run` prints a canned report with no board
attached.

| Read | Settles |
| --- | --- |
| MDIO scan of addresses 0–31 | Which two addresses the PHYs strapped. They are discovered, never computed ([`board.md`](board.md) §3.3) |
| `0xd08:0x11` bit 8, `0xd08:0x15` bit 3 | The strapped RGMII TX and RX delays, which fix the FPGA-side `DELAYG` taps — a lookup, not a sweep |
| `PHYCR2` (reg 25) bit 11, read only | Whether `CLKOUT` is 25 or 125 MHz, which the PLL constraints depend on. The datasheet default and the measurement disagree |
| Frequency counter on `P6` vs `OSCG` | The actual reference frequency, independent of what the PHY registers claim |

Plus the things that must work before anything else does: the JTAG chain reports IDCODE
`0x41111043`, a bitstream loads to SRAM, the PLL locks against the 25 MHz PHY1 generates,
and the console answers.

**Do not write any of those registers, only read them** — `PHYCR2` bit 0 gates the clock
that runs the whole FPGA. See §3a.

A single cable from any spare host port into P0 is also enough to confirm one PHY links up
and auto-negotiates.

## 6. Ethernet and the test rig

Cable one NIC to each RJ45 port. Put each NIC in its own network namespace so the host's
own stack cannot short-circuit the path and make a dead board look alive.
`tools/bench_netns.sh` does the setup, teardown and baseline test, with no interface names
hard-coded:

```sh
sudo tools/bench_netns.sh up enp1s0 enp2s0   # your two NICs
sudo tools/bench_netns.sh ping               # baseline, then again with the board inserted
sudo tools/bench_netns.sh status
sudo tools/bench_netns.sh down               # returns both NICs to the host
```

It creates namespaces `bsw-a` and `bsw-b`, disables RA and autoconf on each interface, and
assigns `2001:db8:1::1/64` and `2001:db8:1::2/64`. The equivalent by hand:

```sh
sudo ip netns add bsw-a && sudo ip netns add bsw-b
sudo ip link set enp1s0 netns bsw-a          # substitute your interface names
sudo ip link set enp2s0 netns bsw-b
for ns_if in "bsw-a enp1s0 1" "bsw-b enp2s0 2"; do
  set -- $ns_if
  sudo ip netns exec $1 sysctl -qw net.ipv6.conf.$2.accept_ra=0 net.ipv6.conf.$2.autoconf=0
  sudo ip netns exec $1 ip link set $2 up
  sudo ip netns exec $1 ip -6 addr add 2001:db8:1::$3/64 dev $2
done
```

```
  step 1, baseline:     NIC A <--------- patch cable ---------> NIC B
                        ping must work before the board is involved

  step 2, insert:       NIC A <--> P0 [ 5A-75B ] P1 <--> NIC B
                        same ping, now through the board
```

**Establish the baseline before the board goes in.** Cable the two NICs directly to each
other and confirm `sudo ip netns exec bsw-a ping -6 -c3 2001:db8:1::2` works. Otherwise the
first failure you debug will be the rig, not the gateware.

Deleting a namespace returns its physical interface to the host, so `down` is a complete
undo:

```sh
sudo ip netns del bsw-a; sudo ip netns del bsw-b
```

Do not put the board in a path carrying traffic you care about.

## 7. Host software

```sh
sudo apt install openfpgaloader picocom iproute2   # or build openFPGALoader from source
sudo cp /usr/share/openFPGALoader/99-openfpgaloader.rules /etc/udev/rules.d/
sudo udevadm control --reload-rules && sudo udevadm trigger
sudo usermod -aG dialout,plugdev "$USER"           # log out and back in
```

The udev rules and group membership are what let you drive the adapters without `sudo`.

## 8. Verify the whole rig

```sh
python3 tools/bench_check.py --cable ft232
```

Standard library only, so it runs on a bare bench host with no virtualenv. Pass your
adapter's cable name; `openFPGALoader --list-cables` lists them. It probes, in order:

| Probe | Checks |
| --- | --- |
| `toolchain` | openFPGALoader on `PATH`, and at least one of picocom/minicom/screen/tio |
| `usb adapters` | `--scan-usb` opens each bridge — distinguishes "plugged in" from "we can talk to it" |
| `serial ports` | Stable `/dev/serial/by-id/*` paths |
| `permissions` | `dialout`/`plugdev` membership and an installed openFPGALoader udev rule |
| `jtag chain` | `--detect` reports IDCODE `0x41111043` |
| `nic pair` | Two NICs that are up-capable, unaddressed and not enslaved |

The first five gate the JTAG-and-console work of §5b; the NIC pair gates the traffic tests
of §6. The exit status is non-zero if any of the first five fail. IDCODE `0x41111043` is
`LFE5U-25` for every speed grade, so it confirms the part but not the revision — read that
off the silkscreen ([`board.md`](board.md) §1).

## 9. Loading bitstreams

**Load to SRAM during bring-up.** It is volatile, so a power cycle undoes a bad bitstream:

```sh
openFPGALoader -b colorlight -c ft232 -m build/diagnostics/gateware/diagnostics.bit
```

Only write flash once a bitstream is known good, since a bad one comes back after every
power cycle:

```sh
openFPGALoader -b colorlight -c ft232 -f build/diagnostics/gateware/diagnostics.bit
```

Recovery from a bad flash image is a fresh SRAM load followed by a flash rewrite; the FPGA
loads from flash at power-on but JTAG always wins afterwards, so the board is not brickable
this way.

The OpenOCD equivalent is in §4.
